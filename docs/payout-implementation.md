# Реализация инспекции выплат

Ветка `ft/XYZ-598/fraudo-withdrawall-impl` основана на
`ft/XYZ-598/fraudo-withdrawall` (финальные изменения после review: `9913262c`).
Используется существующий
`proxy_inspector.InspectorProxy.InspectWithdrawal` из Damsel
`ft/XYZ-599/inspector-payout` (коммит `dfd92e7`).

## Реализованный путь

- Инспекция принимает `WithdrawalContext` до выбора маршрута. Party и Wallet
  берутся из контекста; `shop_id` не подставляется из `wallet_id`.
- Выплата представлена своей моделью `PayoutModel` (Party, Wallet, ID выплаты);
  общие с платежом поля вынесены в `OperationModel`, `PaymentModel` не меняется.
- Поля правил выплат — отдельный `PayoutCheckedField`: только то, что приходит
  в `WithdrawalContext` (email, ip, fingerprint, user_id, phone, карта, валюта,
  Party, Wallet). Платежный `PaymentCheckedField` не содержит `wallet_id`.
  Соответствие полей колонкам задано явно для каждой истории
  (`HistoryFieldResolver`): поле, которого в истории нет, отклоняется,
  а не превращается в пустой фильтр.
- Конфигурация правил выплат приходит через отдельные compacted-топики
  `payout_template`, `payout_template_reference`, `payout_group_list`,
  `payout_group_reference`. Тип операции задаёт топик, отправители пишут
  команды выплат только в payout-топики. Платежные и выплатные
  шаблоны, группы и привязки хранятся отдельно в памяти.
- Результат каждой инспекции выплаты публикуется в топик `payout_result`
  (JSON `PayoutResult`: модель выплаты и результат правил, ключ — ID выплаты).
- Порядок выплатных правил: глобальный шаблон, глобальная группа, группа Party,
  группа Wallet, шаблон Party, шаблон Wallet. Приоритеты группы сохраняются.
  `notify` не скрывает последующее терминальное решение.
- Результат соответствует контракту Damsel: `trust` → `trusted`,
  `accept`/`acceptAndNotify`/`notify` → `low`, `decline`/`declineAndNotify` →
  `fatal`, `highRisk` и отсутствие решения → `high`.
- Валидатор выплат запрещает `3ds`, `isTrusted`, `isMobile`, `isRecurrent`
  и проверяет имена полей по их источнику: текущая выплата (`in`, `like`,
  списки), страна (`countryBy`: ip, country_bank), история платежей
  (`count`/`sum`/`unique`), история выплат (`*Payouts*`, серый список).
- `countPayouts*`, `sumPayouts*`, `uniquePayouts` читают завершённые выплаты
  из ClickHouse. Сначала выбирается последняя запись по ID, затем применяются
  статус, код ошибки и явные группировки. Повторная загрузка одной выплаты
  не увеличивает агрегаты. При одинаковом времени события предпочтение получает
  запись с заполненными Party/Wallet/User. История выплат хранит то, что
  fraudbusters-mg-connector берёт из `WithdrawalState` Fistful: party_id,
  wallet_id, currency, карту, `contact_info` (email, phone), `client_info`
  (ip, fingerprint) и `client_identity` (customer_id, user_id).
- При инспекции выплаты `count`/`sum`/`unique` продолжают читать платежи,
  без добавления текущей выплаты к платежной истории. При инспекции платежа
  прежняя добавка текущего платежа сохраняется.
- `user_id` не подменяется `customer_id`. Отсутствующее значение поля
  или группировки даёт ноль для агрегатов выплат.
  Автоматического ограничения по Party и конвертации валют нет.
- Списки выплат используют `IdInfo.payout_id` и отдельную таблицу менеджера
  списков. Проверяется каскад Global → Party → Wallet, без поиска в платежных списках.
- Management читает payout-топики конфигурации и сохраняет команды и события
  списков выплат в отдельных таблицах. Платежные топики и их ключи не меняются.
- REST-загрузка истории поддерживает optional `partyId`, `walletId`, `customer`.
  Коннектор Fistful передаёт доступные Party и Wallet.

## Данные и включение

Существующие миграции не менялись. Новые изменения аддитивны:

| Владелец | Миграция | Изменение |
|---|---|---|
| fraudbusters / ClickHouse | `src/main/resources/db/migration/V13__add_payout_identity.sql` | Nullable-поля идентичности выплат |
| fraudbusters-management / PostgreSQL | `V20__payout_configuration.sql` | Отдельная проекция конфигурации и списков выплат |
| wb-list-manager / PostgreSQL | `V1.1__payout_rows.sql` | Отдельное хранилище выплатных списков |

У старой истории новые поля остаются NULL. Существующие платежные таблицы,
ключи и данные не перезаписываются. Новые события могут постепенно дополнять
историю выплат. Страна банка для новых выплат записывается в существующий
`issuerCountry`; старое назначение `bankCountry` сохраняется.

Перед включением нужны следующие шаги, которые эта реализация не выполняет:

1. Выпустить используемые версии артефактов: Fraudo `1.1.0`,
   fraudbusters-proto `1.137-211f642`, wb-list-proto `1.52-211f642`,
   swag-fraudbusters `1.122-ca31113`, Damsel `1.717-dfd92e7`,
   fistful-proto `1.201-6e551cb` (master `6e551cb`; на Maven Central пока
   только `1.196-d7dfd45` без `client_info` и `client_identity` в выплате).
   Для Damsel можно взять опубликованный `1.714-09f693a`: файлы
   `proxy_inspector`, `withdrawals_domain`, `domain`, `base` в нём совпадают
   с `dfd92e7`.
   Проверки выполняются с локально собранными артефактами этих исходников;
   локальная сборка не означает публикацию релиза.
2. Применить ClickHouse V13 до начала записи расширенной истории.
   В сервисе нет автоматического Flyway для ClickHouse; PostgreSQL-миграции
   проходят через существующий Flyway. Для локальной инфраструктуры дополнен
   `ensure-current-schema.sql`.
3. Создать топики `payout_template`, `payout_template_reference`,
   `payout_group_list`, `payout_group_reference` (compacted) и `payout_result`
   до запуска сервисов: fraudbusters предзагружает правила выплат из этих топиков.
   Отправители payout-команд пишут их только в payout-топики.
4. Подключить вызов `InspectWithdrawal` со стороны обработки выплат.
   Эта ветка реализует сторону fraudbusters и не меняет исполнение выплат.

Удалённый в базовой ветке inline-синтаксис `isTrusted` не восстанавливается:
по подтверждению владельца, таких сохранённых шаблонов нет. E2E использует
поддерживаемую форму `isTrusted("имя шаблона")`.

## Оставлено за пределами изменения

- REST/UI для редактирования и просмотра выплатных шаблонов, групп и списков.
  Существующие платежные экраны по-прежнему работают с платежными таблицами;
  выплатная конфигурация доставляется Thrift-командами через payout-топики.
- Выплатная эмуляция на историческом наборе (`full_*`-топики для выплат не заведены),
  пагинация истории выплат, отчётность и потребитель `payout_result`
  с хранением результатов инспекции выплат.
- Исправление существующей предзагрузки исторических платежных правил:
  при `kafka.historical.listener.enable=true` StartupListener использует текущие
  типы слушателей и для исторической предзагрузки. По умолчанию эта настройка
  выключена; её включение требует отдельной проверки и исправления.

## Проверки

Проверены общий язык и генерация контрактов, независимые сборки затронутых
сервисов, PostgreSQL/ClickHouse-совместимость и платежный E2E. После исправлений
отдельно повторены затронутые сценарии инспекции, истории, списков и маршрутизации
команд management. Исходные шаблоны в базе и базовая ветка языка не менялись.

Также выполнены 47 CI-тестов, root `npm run check` и 10 UI-тестов.
Стандартная production-сборка UI останавливается при недоступности Google Fonts;
компиляция с `--optimization=false` проходит. Код UI не изменялся.

Обновление после финального review языка использует типизированные ключи
`HistoryCacheKey` и фабричный `FirstFindRulesWithPayoutVisitor`. Сервис сохраняет
зависимость от `FirstFindVisitorImpl`, возвращаемого фабрикой, и не обращается
к внутренним ключам кэша. Дополнительно проверены независимость платежных и
выплатных агрегатов в одном правиле и очистка кэша между инспекциями.
